Proposed evidence records

Use a separately versioned current bridge namespace; leave every historic archive,
approval, pin, source-commit binding and measurement immutable. The design proposes:

1. A baseline-content identity record: exact PR587 commit/tree, all canonical
   members and modes, protected merge/approval payload references and their seals.
   It claims retained authenticated content, not a fresh remote state or Git read.
2. A current-source record: exact complete raw file inventory, current commit/tree,
   its real local parent, producing runtime, lock, generator and environment pins.
   Future validation must independently compare the actual disposable checkout and
   committed raw blobs. Do not infer these facts from a successful status command.
3. A complete change ledger: all 810 PR587 differences, with exact before/after
   identities, owner changes, source obligation, approved exception rationale,
   preservation route, affected operations/consumers and remaining controls.
4. A per-file preservation recipe registry: exact old and current member hashes,
   literal definition maps and only bounded approved transformations. It has no
   blanket test-only exemption, ignored path family or arbitrary expected-value map.
5. A current applicability record: every policy/tool/external input and exact
   operation route, review identity and validation evidence. Historical performance
   reports remain scoped to their original measurement cohort and producing source.

Those records describe actual source, not acceptance booleans supplied by a report.
The existing legacy adapter must keep its old exact cohort and ancestry behavior.
The current cumulative route must be selected explicitly by version and exact
identity. A legacy failure, missing Git access or absent receipt must not silently
fall back to the new route. No path is accepted merely because an archive exists.

Live-successor validation must precede predecessor exposure

For each historical test request, the proposed reader must execute this order:

1. Authenticate registry version, complete membership and exact recipe bytes.
2. Validate owned regular paths; reject aliases, symlinks, traversal, duplicates,
   missing/extra successors and wrong current byte identities.
3. Validate every live definition and helper/fixture/import initializer used by
   that recipe, including transitive shared modules. Verify actual collector/definition
   destinations; an unexecuted archive is not a live replacement.
4. Compare original function/decorator/parameter/assertion ASTs with multiplicity
   and expected statement order. For fixture or source-correct assertion changes,
   allow only named exact transformations bound to the accepted source and specific
   original owner. All other old statements, definitions and initializers stay exact.
5. Require the recipe's positive and sensitivity controls and exact-head review.
   Source documentation alone supplies no run credit. Unresolved recipes fail closed.
6. Only then return the authenticated predecessor bytes for historical readers.
   Live audits continue to use real live nodes and must never parse an old substitute
   as if it certified the current consumer.
