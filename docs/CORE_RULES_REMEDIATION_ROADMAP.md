## Where this stands

This roadmap is the closure inventory for Warhammer 40,000 11th Edition Core Rules categories 01–25. The audited runtime is `55780340` ([PR #503](https://github.com/SobolGaming/Warhammer_40k_AI/pull/503)); the compact documentation baseline is merged [PR #504](https://github.com/SobolGaming/Warhammer_40k_AI/pull/504).

Orders 1–83 are merged. The requested Order 84 audit surveyed all 25 categories and 59 FAQs without stopping at the first finding. It found 11 follow-ups, now Orders 84–94; `PFINAL` moves to Order 95. `CAUDIT-01` remains open and Core Rules are not certified. Category 07 still requires final revalidation. See the [generated audit report](ORDER_84_AUDIT_REPORT.md) and [evidence and limits](ORDER_84_AUDIT_NOTES.md).

[ARCHITECTURE_V2.md](../ARCHITECTURE_V2.md) records which engine phases landed. Those phase labels are build history. When a phase record and an order in the table below disagree, the order is the rules behavior on `main`. Faction work is out of scope here and waits on `PFINAL`; see the [faction roadmap](FACTION_RULES_REMEDIATION_ROADMAP.md).

Per-order source tuples, owner traces, and validation stay in `docs/ORDER_*_SCOPE_PLAN.md`, `docs/ORDER_*_PREFLIGHT_AUDIT.md`, and `docs/performance/order*/`. This file no longer copies those journals.

## Authority

Policy ID: `core-rules-source-policy:maintained-direct-app-data-mirrors:2026-09-02`.

40k.app and [Game Datamissions](https://game-datamissions.com/11th/rules/changelog) are co-equal non-affiliated maintained App-data mirrors. They are not Games Workshop. The live sites are not runtime inputs. Maintained App wording supersedes an older PDF. If co-versioned mirrors disagree for one stable rule ID and App-data version, loading fails closed until an official-App comparison.

Every implementation observation pins provider, URL, App-data version or observation timestamp, transcription SHA-256, and source-observation fingerprint. `S-MIRRORS` (Order 11, PR #416) is that governance gate. P00 is PR #405 and changes provenance only.

The retained official Core Rules PDF SHA-256 is `f6a2443a44627ac5f0ef08407d29aa5ec7e97339998f05bc35f3ae37bf276833`. App-data 931 (2026-08-26) is 18 distinct obligations. App-data 946 (2026-09-02) adds 18.04.01 Rapid Disembark. Both are rows in the table below.

Only one remediation implementation PR is open at a time. It is reviewed and merged before the next implementation starts. The Order 84 audit enumerates all discovered follow-ups together; it does not implement or close them.

## How a row closes

| Gate | Meaning |
|---|---|
| `APP-AUTHORITY` | A hash-pinned maintained-mirror observation is the controlling source |
| `APP-DRIFT` | A repository row or older PDF differs from current App wording and must be narrowed |
| `APP-INTERNAL-DRIFT` | The App corpus disagrees with itself. Bind by title and operative text |
| `IMPLEMENTATION-GAP` | The source wording stands. The engine proof or consumer was wrong |
| `SOURCE-GOVERNANCE` | Source policy or complete retained observation evidence requires closure |
| `REVALIDATE` | No separate PR. The category still passes `PFINAL` |
| `FINAL-CERTIFICATION` | Fresh audit of all 25 categories against one selected snapshot |

`T-TRANSPORT` means P18A, P18C, P18D, P18E, P18F, P18G, P18H, and P18B are all merged. A narrower definition has to be written here before it is used.

`PFINAL` depends on every prior roadmap row, including source-governance rows `P15J` and `S-MIRRORS`. The roadmap parser expands that aggregate into the ordered PR IDs; newly inserted rows automatically become certification prerequisites.

For merged Orders 1–83, the fourth column is the defect the order closed. For unmerged Orders 84–94 it is the outstanding finding. The fifth column is the required behavior. The sixth column is the source locator that the owning PR must pin. For merged rows, do not read the fourth column as the behavior on `main`.

## Resolved exceptions `PFINAL` still rechecks

Shock Disembark engagement: C18-07's source exception was resolved by the repository owner on 2026-09-19. Passengers may set up engaged with any enemy, and that engagement feeds the opponent Fight queue. Embarked passengers do not inherit the Transport's prior engagements. Evidence: [Order 62 scope](ORDER_62_SCOPE_PLAN.md).

Consolidation responses: owner-confirmed official App v946 (2026-09-21) gives forced enemy selection to Engaging only. Ongoing preserves prior engagements. Objective stays unengaged and in range. Evidence: [scope, source resolution and validation](ORDER_72_SCOPE_PLAN.md).

## Compliance claim

The project may claim Core Rules categories 01–25 compliant only after every implementation PR, `S-MIRRORS`, and `PFINAL` are merged, including any further PR the audit inserts, and a fresh 25-category audit on `main` finds no new gap. The claim names the selected snapshot, provider, and observation date, and it excludes factions and every scope `AGENTS.md` prohibits.

`PFINAL` requires a clause and FAQ inventory mapped to an immutable source observation, an engine owner, and a facade regression. Loaded source rows, passing tests, and merged orders are not that inventory. Complete-game performance remains a separate [performance policy](performance/PERFORMANCE_POLICY.md) and is not certified here.
