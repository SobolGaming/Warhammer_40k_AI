# Contract 8 to Contract 9 migration

Contract 9.0 publishes the Phase 17N Step 4 Primary Mission state and choice
contract. `GameViewPayload` now requires the public
`primary_mission_progress_state`, and the shared finite-decision path exposes
`select_primary_mission_choice`. Contract 9 retains Contract 8's two directed
Primary Mission assignments, grouped turn-start position history, destruction
attribution, battlefield-departure evidence, and battlefield geometry.

This is a deliberate major-version break. A Contract 8 projection or replay
does not contain enough evidence to reconstruct persistent mission markers,
historical condemned selections, or consecration designations. Contract 9 does
not invent empty progress, infer it from current geometry, or replay past turns
to synthesize it. Contract 8 payloads remain valid only against the separately
retained 8.x deployment.

The changed payload-family identities are:

- `game-view-v11-phase17n-step4` and the corresponding
  `contracts/v8/game-view.schema.json` URI;
- `decision-request-view-v5-phase17n-step4` and the corresponding
  `contracts/v6/decision-request-view.schema.json` URI;
- `lifecycle-status-v4-phase17n-step4` and the corresponding
  `contracts/v4/lifecycle-status.schema.json` URI;
- `session-projection-v7-phase17n-step4` and the corresponding
  `contracts/v8/session-projection.schema.json` URI;
- `event-delta-v4-phase17n-step4` for in-process integer cursors and
  `event-delta-v5-phase17n-step4` for authenticated HTTP cursors;
- `session-metadata-v9-contract`, `session-command-result-v9-contract`, and
  `session-command-outcome-v9-contract`; and
- `replay-artifact-v7-phase17n-step4` and the corresponding
  `contracts/v7/replay-metadata.schema.json` URI.

The live decision-family schema URI advances to
`contracts/v7/decision-family-live.schema.json` because its definitions inherit
the new decision-request family. The nested
`battlefield-view-v4-phase17n-step3` family is unchanged: Step 4 does not change
the coordinate system, authoritative geometry, interaction overlays, render
hints, or geometry-hash semantics. All other request and response family
versions are unchanged unless listed above.

## Public Primary progress state

`primary_mission_progress_state` is public mission audit state. Players,
coaches, delayed spectators when their projection reaches the event, replay
viewers, and administrators receive the same visible rows. It contains three
deterministically ordered collections:

- `markers` records stable marker, game, owner, mission, source-rule,
  source-descriptor, marker-kind, and anchor identities. An anchor is exactly
  one objective marker or terrain feature. Creation provenance binds the
  battle context when applicable and the source event plus optional result,
  Action, destruction, and designation IDs. Removed markers remain as
  `status: "removed"` tombstones with complete removal context and source,
  event, result, and Action provenance; clients must not treat absence as
  removal.
- `condemned_selections` records each Punishment turn's candidate policy,
  complete candidate rules-unit and evidence sets, selected rules-unit set,
  selection bounds, fallback use, optional request/result identities, and
  source event. An automatic empty resolution is an explicit historical row,
  not an absent value.
- `consecration_designations` records the designated rules unit and physical
  components, source destruction, creation event and battle context, most
  recent declined-resolution provenance, and `active` or `consumed` status. A
  consumed designation binds its created marker and complete consumption
  context; declined designations remain active but cannot prompt twice in the
  same owner turn.

These records are engine-owned. Clients may render and cache them as part of a
projection but must not create markers, remove tombstones, condemn units,
consume designations, or derive scoring state from current battlefield
geometry.

## Finite Primary Mission choices

Every Step 4 player choice uses one public
`select_primary_mission_choice` `DecisionRequest`. The unselected request
payload contains `game_id`, `choice_kind`, `player_id`,
`primary_mission_id`, source descriptor and rule IDs, optional round/phase,
optional subject and source Action IDs, the complete `legal_target_ids`, empty
`selected_target_ids`, evidence IDs, and the fallback flag. Each finite option
contains the same strict payload with its exact selected target set.

Option IDs use the deterministic `primary-mission-choice:<sha256>` family and
bind the game, choice kind, player, source descriptor, subject, source Action,
and selected target IDs. The digest is opaque to clients. Adapters submit one
engine-emitted option ID and never construct an ID or mutate state from an
option payload.

The four choice kinds and option sets are:

- `locate_and_deny_setup`: at the final start-battle boundary, each player
  assigned Locate and Deny selects exactly five logical terrain areas outside
  their deployment zone, or every available area when fewer than five exist.
  Every legal exact set is an option. The accepted choice creates one friendly
  operation marker per selected area.
- `punishment_condemnation`: at the start of the assigned player's turn, the
  engine offers every one-, two-, and three-unit subset, capped by the
  candidate count, from enemy battlefield rules units that are in objective
  range or are authoritative previous-turn destroyers of friendly units. If
  that preferred set is empty but enemy battlefield units exist, options are
  exactly the single-unit fallback choices. If no candidate exists, the engine
  records one automatic empty resolution and emits no pending decision.
- `consecrate_objective`: at the assigned player's turn end, one request is
  emitted for each unresolved active consecration designation. Options are one
  eligible non-home, not-already-friendly-consecrated objective in range of
  the designated rules unit, plus the empty `Decline this choice` option.
  Selecting an objective creates a consecrated marker and consumes the
  designation; decline records that designation as resolved for the current
  owner turn without consuming it.
- `sensor_sweep_marker_removal`: after a qualifying Sensor Sweep Action has
  completed, each option selects exactly one eligible active operation marker.
  `sensor-sweep-locate-and-deny` selects a friendly marker and
  `sensor-sweep-extract-relic` selects an opponent marker. Acceptance changes
  that row to a provenance-complete removed tombstone; it never deletes the
  marker.

The existing `start_mission_action` finite family starts the ten source-backed
Primary Actions: `commit-sabotage`, `decoy-objective`,
`extract-intelligence`, `maintain-control`, `secure-asset`,
`sensor-sweep-extract-relic`, `sensor-sweep-locate-and-deny`,
`surveil-enemy-unit`, `triangulate-objective`, and `vanguard-operation`.
Adapters still select only the emitted
`start:<mission_action_id>:<unit_instance_id>:<target_id>` option. The engine
owns eligibility, Action persistence, completion conditions, marker creation,
status effects, and follow-up choices.

## Validation, ordering, events, and replay

The lifecycle recomputes the complete authoritative Primary choice request
before queue pop, `DecisionRecord` creation, or mutation. Request, actor,
choice kind, source, timing, subject, source Action, legal-target, evidence,
fallback, option-ID, or option-payload drift returns a typed invalid status
with `invalid_reason: "primary_mission_choice_request_drift"` and
`field: "authoritative_request"`. Malformed payloads, invented options,
wrong decision types, and schema-invalid submissions likewise leave the
pending request and authoritative progress unchanged.

Step 4 timing is deterministic:

1. Locate and Deny requests drain at the final setup/start-battle boundary
   before the setup completion gate enters the battle.
2. Punishment drains at the start of the active player's Command phase, after
   battle-round-start hooks and before ordinary phase-start windows and the
   Command phase body.
3. At the end of a player turn, the engine records the authoritative turn-end
   objective-control boundary and resolves started Primary Actions before
   opening Step 4 turn-end choices. Completed Sensor Sweep marker removals are
   offered before Consecrate designations. One pending request is resolved at
   a time and the opportunity is recomputed before the turn can advance.
4. Surveil the Foe's move-triggered marker removal is automatic at the shared
   phase-flow boundary for each unprocessed completed-move event; it is not a
   client-authored choice.

The public event graph includes `primary_mission_choice_requested`,
`primary_mission_choice_resolved`, `mission_action_completed`,
`primary_consecration_unit_designated`, and
`primary_surveil_move_marker_removal_resolved` as applicable. Every
`primary_mission_choice_resolved` payload carries `choice`, `request_id`,
`result_id`, `selected_option_id`, `automatic`, `created_markers`,
`condemned_selection`, `updated_designation`, and `removed_marker`; automatic
Punishment uses null request/result/option IDs. Action completion events carry
the complete `mission_action_state` and optional `primary_mission_marker`.
Stable state IDs and source-event links make these events JSON-safe,
deterministic, and cross-checkable in replay.

The Contract 9 replay loader accepts only
`replay-artifact-v7-phase17n-step4`. It restores pending finite choices and the
complete progress state, then validates marker, condemnation, designation,
Action, decision, destruction, and event relationships. It rejects Contract 8
v6 artifacts before restoration and never synthesizes missing Step 4 state.

Clients upgrading from Contract 8 must:

1. regenerate models from the Contract 9 OpenAPI and JSON Schemas;
2. require and retain the complete public `primary_mission_progress_state`;
3. add a generic finite-option presentation for
   `select_primary_mission_choice` and submit only emitted option IDs;
4. treat a typed invalid result as non-consuming and refresh the current
   projection/request before retrying;
5. preserve the published timing and event order instead of locally completing
   Actions or applying marker/designation state; and
6. discard cached Contract 8 projections, event cursors, projection hashes,
   session metadata, replay metadata, and checkpoints, then fetch a fresh
   authenticated Contract 9 projection before submitting another command.
