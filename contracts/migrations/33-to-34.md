# Contract 33 to 34: detachment construction records

Contract 34 requires `canonical_detachment_id` and `construction_constraints` in
every serialized DetachmentDefinition. The canonical ID is a reviewed project
identity shared by aliases, not a display name or provider-local reference ID.
Constraint records carry stable constraint/source IDs and one correctly typed
unit or other-detachment selector. An empty list means no recorded constraints;
an absent field is invalid. Do not manufacture empty records to migrate unknown
external content. Rebuild it from its reviewed source on the new release.

Canonical catalog packages now use `canonical-catalog-v2-construction`.
Operator persistence uses `session-persistence-v26-construction`; replay uses
`replay-artifact-v28-construction`. Old saves and replays require the release
matching their catalog and engine identity. There is no compatibility fallback.
The session metadata/command wrappers advance to their v34 contract identifiers.
Ordinary player-list inputs remain v2 because their roster selection shape is
unchanged; selected catalog identities are resolved by the engine.

The existing fixed pre-game roster path owns these validations for every adapter.
New source-attributed violation codes are `required_unit`, `prohibited_unit`,
`required_other_detachment`, `prohibited_other_detachment`,
`construction_constraint_invalid`, and `attachment_declaration_invalid`.
Structural construction rules apply even when a test request relaxes unrelated
points/Warlord certification. No decision envelope or hidden-information policy
changes. No faction-specific constraint records are populated in this release.

Keep the 33.x deployment available through at least 2027-09-21 and one released
34.x minor line, whichever is later. Released compatibility baselines remain
immutable. Regenerate engine identity, the new major baseline, external examples
and the TypeScript client; run the exact PR-base compatibility check and installed
wheel smoke before publishing.
