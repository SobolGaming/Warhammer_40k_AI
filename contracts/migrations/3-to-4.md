# Contract 3 to Contract 4 migration

Contract 4.0 makes the engine-owned `spatial_context_hash` a required member of
published movement and placement proposal requests. It is intentionally not
wire-compatible with Contract 3.

Clients must regenerate models from Contract 4 OpenAPI and schemas, then:

1. require `spatial_context_hash` on every movement or placement
   `proposal_request` and treat it as an opaque engine-owned value;
2. never derive proposal validity from the viewer-scoped
   `authoritative_geometry_hash`, which remains informational;
3. submit only against the current pending request ID and discard any cached
   physical proposal request after reconnect, resynchronization, or a state
   generation change;
4. require `session-metadata-v4-contract`,
   `session-command-result-v4-contract`, and
   `session-command-outcome-v4-contract` on the formal session protocol;
5. use a separately deployed 3.x adapter for clients that cannot migrate
   during the published support window.

There is no content negotiation between majors. A request with a mismatched
payload `schema_version` fails before engine mutation.
